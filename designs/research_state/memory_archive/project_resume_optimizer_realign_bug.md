> **Archived 2026-09-08** — fixed and hardened (name-keyed remap, ac5b93f); the guard is in-tree. Preserved verbatim; nothing below is current.

2026-06-21 (fix SHIPPED, commit e1a6513). ai_v6_13 (the live run) terminated at 22.4M with `RuntimeError: The size of tensor a (128) must match the size of tensor b (5) at non-singleton dimension 1`, MASQUERADING as a clean "Training complete / 85.8%" (see below). The user's hypothesis "is it the IV-prediction change?" was CORRECT — but the mechanism is a RESUME bug, not a forward bug.

**ROOT CAUSE (definitive, reproduced + pinpointed):** the crash is in `AdamW.step()` (`instrumented_ppo.py:1267` → `_multi_tensor_adamw`), NOT the forward. SB3/torch save+load the optimizer state **by parameter POSITION, not name**. The v40 nature/EV commit (e7fc652, `gen3_nature_ev_belief_v1`) REORDERED `SpreadBelief.__init__` (now builds `reinject`/`norm` BEFORE `stat_head`; pre-v40 had `stat_head` first). ai_v6_13 started 0620 on pre-v40 code, then resumed 0621 under `--sync-to-main` onto v40 → **weights loaded fine (name-keyed → arch check PASSED) but the position-keyed Adam momentum (`exp_avg`/`exp_avg_sq`) got assigned to the WRONG SpreadBelief params** (the permutation baked into the saved values). It crashes only when a misassigned param of a DIFFERENT shape first gets a gradient — data-dependent, so it survived ~5 train() calls. Diagnostic (load ckpt, compare each param.shape vs its exp_avg.shape) showed 10 mismatches, ALL in `features_extractor.spread_belief.{reinject,norm,stat_head}` (128=D_MODEL, 5=N_SPREAD_STATS). 128-vs-5 was a 2D `[out,in]` weight mismatch (reinject.weight (128,5) ↔ stat_head.weight's (5,128) momentum).

**SECONDARY BUG (also fixed):** `train_rl_agent.py:2546` `except Exception` SWALLOWED the crash — printed only `str(e)` (no traceback), saved `final_model_exception.zip`, then FELL THROUGH to the normal save + "Training complete" + final eval + exit-0. So the launcher saw a clean exit, didn't auto-restart, and reported a fake 85.8% final win-rate. This is why "0→22M looked clean" was untrustworthy (earlier sessions may have hit the same bug, masked). FIX: print full traceback + RE-RAISE (graceful SIGTERM uses os._exit(15), never hits this except, so safe).

**THE FIX (BUILT, suite-green, GPU-verified):** `train_rl_agent._validate_or_reset_optimizer_state(model)` runs on every resume (right after load, before any LR read) — checks each optimizer param's `exp_avg`/`exp_avg_sq` shape vs the param shape; on ANY mismatch (proof the position-keyed state is misaligned; same-shape permutations are undetectable so the whole state is distrusted) it DROPS the entire optimizer momentum (`opt.state = defaultdict(dict)` → fresh zero-init; LR/param_groups preserved; re-warms in a few hundred steps — negligible on a 22M-step resume, strictly better than scrambled/crashing momentum). General (any future param-reorder), not SpreadBelief-specific.

**VERIFIED:** reproduced the exact crash by resuming a COPY of `final_model_exception.zip` on the idle GPU (bridge, exact arch flags) → crashed at 22.4426M; with the fix, the guard printed "10 shape mismatches → RESETTING momentum" and trained PAST to 22.4754M with no crash. Regression test `src/main/resume_optimizer_realign_test.py` (4 tests: aligned=no-reset, misaligned=reset, LR preserved, no-optimizer no-op) + full suite 2965 green. Doc note added to `src/agents/model/CLAUDE.md` (reorder hazard).

**LESSONS:** (1) ~~NEVER reorder an existing module's params in `__init__` — APPEND LAST~~ — **SUPERSEDED by the name-keyed remap below; append-LAST is no longer load-bearing for optimizer correctness** (still good hygiene). (2) A broad `except` around `model.learn` that continues to "complete" MASKS fatal crashes as successes + defeats launcher auto-restart.
