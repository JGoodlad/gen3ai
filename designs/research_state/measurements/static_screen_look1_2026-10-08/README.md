**The interpretive fork (FINDING).** §8.1's outcome table was written for one look at 2.132; §8.2 replaced that

three-look design, so `read_look1.py` declares (before the read) the boundary reading as the outcome and reports
the fixed-sample one beside it. The orchestrator owns the call.

## The speed rule (registered in-arm s, REPORTED): s = −3.7 % ⇒ s ≤ 5 %, the strength rule alone decides

`speed_read.py` → `speed.json`. A cycle is the wall between consecutive `train/train_ms` records within ONE child's
TensorBoard file (never across a stop / resume). Excluded: every child's first 11 updates (its start / resume window,
s_read's canary rule; applied to fresh launches too, so both arms lose the same cycles), a non-advancing record (the
save dump), a compile-canary verdict in the window, an in-loop eval overlapping it, and any CPU-sampler row
(`~/.claude/jobs/st_screen/<run>*.cpu.jsonl`) in the window with contention factor ≥ 1.05 (or none).

| arm | quiet cycles kept / total | per seed (s1001 / s1002 / s1003) | per-seed median (s) | pooled median (s) |
|---|---|---|---|---|
| legacy | **179 / 456** | 38 / 60 / 81 | 60.85 / 58.81 / 58.40 | **58.96** |
| static | **203 / 471** | 44 / 49 / 110 | 58.19 / 58.49 / 56.53 | **56.76** |

**s = 56.76 / 58.96 − 1 = −3.7 %** (static's cycle is shorter). Robustness: the mean of per-seed medians gives
−2.7 %, the median of per-seed medians −1.1 %; the update phase alone (`lifecycle/update_wall_s` on the kept cycles)
45.4–45.6 s vs 46.7–46.8 s, static ~2.6 % faster; END-TO-END wall per run (downtime between children removed, every
restart's startup included) 2.70 h vs 2.66 h, +1.4 % (the resumes' extra startups). All under 5 %. §6.2 predicted
+1.3–1.5 % extractor FLOPs; the measured cycle is not slower. S3 contributes 110 of static's 203 quiet cycles (its
post-switch segment ran on a quieter box), so the pooled median leans on it; every reading above agrees on the rule.
