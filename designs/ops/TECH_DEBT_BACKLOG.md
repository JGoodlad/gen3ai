**Two rules (owner, 2026-09-06).** (1) During the week nothing here is dispatched on the
orchestrator's own initiative: the orchestrator ADDS rows; the owner moves a row to ACCEPTED, and an
ACCEPTED row is dispatched under [`ORCHESTRATOR_SOP.md`](ORCHESTRATOR_SOP.md) §2. (2) **Whatever
quota remains before the weekly reset is burned down on this list as a standing housekeeping
procedure** — ACCEPTED rows first, top to bottom; then PROPOSED rows by **the highest tier across ALL
categories first, and within a tier the smallest row first** (whatever category it sits in). If
ACCEPTED is empty and quota remains, the orchestrator notifies the owner with the top PROPOSED rows
by that order and, absent a reply in 15 minutes, starts the first one. Read the reset time with
`python3 ~/.claude/skills/usage-limits/check_usage.py` (the weekly window resets **Tuesdays ~14:00
PT**). **Target: the weekly quota is used up to 95% by Tuesday ~08:00 PT** (owner, 2026-09-06),
leaving ~5% spare for an issue — so the burn-down is PACED to land there (it starts Monday, earlier if
the backlog is large) and STOPS at 95%: burn-down agents run under the usage gate at
`--weekly-threshold 95`, never higher. The live arm's needs always come first; the burn-down uses
what the arm does not.

| tier | means |
|---|---|
| **P0** | a GIGO class: could make a measurement or a test lie |
| **P0 at the next obs ARCH change** | a P0 that is BATCHED into the next deliberate observation-architecture change (owner, 2026-09-24), so no fork of an existing checkpoint breaks for it alone; the burn-down does not pick it on its own |
| **P1** | blocks or slows correct work (a gate near its bound, a tool that will vanish, a doc every session loads), or is a live-ladder crash |
| **P2** | hygiene and cost |

**Sizes:** XS < S < S–M < M < L. "S each" sorts as S; an owner-gated or research-gated row sorts by
its own size and says what it waits on. Each row carries its size; an ACCEPTED row also carries its
acceptance test ("done when"). A row is DONE when that test is in the routine suite or its artifact
is on main, and moves to §3 with the commit.

**How this file is organized (keep it this way).** §2 is split into CATEGORY subsections, each one
table sorted by tier, then by size (smallest first). **A new row goes into its category AT ITS TIER
AND SIZE POSITION — never appended at the bottom of the file**, and never below §3. If no category
fits, add one and say why in its heading line. A row that closes (fixed, moot or obsolete) becomes ONE
LINE at the top of §3 — title, reason, evidence (a commit, a test, a deleted path); never the story,
which git keeps. A PARTLY done row stays, trimmed to what remains. Keep each row's **bold first phrase** (its title) unchanged when editing, so a concurrent edit can find
it. A model / observation / research proposal does not belong here: put it where the first paragraph
says and leave a one-line pointer at the end of §2.
