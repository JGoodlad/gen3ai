**The cycle estimate (Amdahl), the arithmetic.** X26's live cycle on the 3080 Ti is 74.8 s per 98,304 steps:
`train/train_ms` 42.24 s + `rollout/collect_ms` 26.97 s + 5.6 s of everything else (98,304 / `time/fps` 1,314 =
74.8 s; `main.ops.tb_read rb_x26_s2601 --last 20`, 2026-10-18). Of the collect, 37.39 ms x 416.5 host steps = 15.57 s
waits on the GPU (T2), and 11.40 s is the host CPU's (the Rust core and the host side of T2), which no card changes.
For card `c` against the reference `r`:

    train_c   = 42.24 x U_c / U_r                    U = the bf16 update (s)
    collect_c = 11.40 + 15.57 x W_c / W_r            W = the collect phase's GPU wait per host step (ms)
    cycle_c   = train_c + collect_c + 5.6            speedup = 74.8 / cycle_c
    floor     = 74.8 / (train_c + 26.97 + 5.6)       (only the update speeds up)

Worked for the 600 W 5090: 42.24 x 18.64 / 40.02 = 19.67 s; 11.40 + 15.57 x 18.81 / 40.05 = 18.71 s; cycle 19.67 +
18.71 + 5.6 = 43.98 s → **1.70x, ~2,235 env steps/s against today's 1,314**. The GPU wait reads mostly the CARD, not
the host: the same 3090 waited 41.0 ms on a Zen 3 host and 40.0 ms on a Zen 4 one. Small-batch inference rewards
clocks more than the update does, so the newer cards gain more in collection than in the update (5070 Ti: 1.39x
less wait, 1.13x faster update). **UNVERIFIED** until the local row lands: that our 3080 Ti equals the 3090 here.
Supporting evidence: the 3080 Ti's last local bf16 update was 41.2-41.3 s (`cuda_build_2026-10-12`) and X26's live
one 42.2 s, against the 3090's 40.0-40.1 s.

**Does 16-32 GB of VRAM unlock anything? Not at today's shape.** The production update peaks at 6.1-6.2 GiB reserved
on every card. The larger micro-batches at the same effective batch save at most ~7 % (3090: 40.0 → 37.1 s at
8,192) and ~2-4 % on the 4090 and the 420 W 5090, and they are SLOWER on the 600 W 5090 (+3.5 % at 4,096, +8 % at
8,192). They need 12.0-12.4 GiB (4,096, which
already does not fit the 12 GB 3080 Ti) and 22.9-24.3 GiB (8,192, a 24 GB+ card only). VRAM matters only if the
model, the batch or the env count grows. More envs were not measured.

**What the workload rewards.** Clocks and a newer generation, not bandwidth or datacenter FLOPs. The A100 (1.56 TB/s,
1.41 GHz) is 0.84x a 3090. The 5070 Ti (896 GB/s) is 1.13x. The 5090 at 2.9 GHz is 2.15x. This matches the
2026-09-28 profile: thousands of small, mostly memory-latency-bound kernels per micro-batch, GPU 99 % busy.

### The recommendation (owner's decision; the fit facts are UNVERIFIED for our exact case)

1. **Buy the RTX 5090 if the case and PSU can take it.** It is the only card that changes the regime: est. 1.63-1.70x
   on the whole training cycle (floor 1.38-1.43x), 2.0-2.15x on the update, and 32 GB of room to grow. Power-capped
   to 420 W it still kept 91 % of the 600 W card's update speed (20.44 vs 18.64 s). So **an ITX build can run it
   power-limited** (`nvidia-smi -pl`) and keep most of the gain. Fit (**UNVERIFIED**, NVIDIA's published figures; our
   case model and PSU are not recorded in the repo): the Founders Edition is 2 slots, 304 x 137 mm, 575 W board
   power, 1,000 W PSU recommended, one 12V-2x6 connector. Partner cards are mostly larger. Check the case's GPU length
   and slot clearance, and the PSU's wattage, form factor (SFX / SFX-L) and native 12V-2x6 cable. Expect to need a
   ~1,000 W SFX-class PSU, or to power-limit.
2. **The RTX 5080 is the low-risk fit.** Est. 1.24x cycle (1.27x update) measured CAPPED at 300 W, so a stock 360 W
   card may do a little better (**UNVERIFIED** how much). Its 360 W board power is about our 3080 Ti's 350 W
   (**UNVERIFIED**: likely no PSU change; the FE is 2 slots, 304 mm). Same 16 GB class as headroom needs today.
3. **Not the 5070 Ti** (1.13x update / est. 1.14x cycle: too little to justify a swap). **Not the 4090** (dominated:
   slower than a 5090, and 450 W in a typically 3-slot+ card; the FE is 3 slots / 61 mm). **Not an A100** (slower).
4. **Rent vs buy:** a 5090 rents at $0.50-0.94/h here, so ~$360-680 a month at 24/7. The purchase price is
   **UNVERIFIED** here (the memory note's estimate was $5k+; NVIDIA's launch MSRP was $1,999). At $2,000-5,000 a card
   pays for itself in ~3 months ($2,000 against $680 a month) to ~14 months ($5,000 against $360 a month) of the 24/7
   training the box runs today. Whatever the prices, the 5090 is the one card whose speedup is large enough to change
   run planning: the others buy 1.1-1.4x.

## 2. The real benchmark — the procedure (as run 2026-10-18)

```bash
export PYTHONPATH=$PWD/src:$PWD PY=/home/goodlad/miniconda3/envs/gen3ai_torch28/bin/python3   # repo root
$PY -m tools.cloud.vast.cli verify-zero && $PY -m tools.cloud.vast.cli search --gpu "RTX 5080"   # read the ranked list
$PY -m tools.cloud.vast.cli create --offer auto --gpu "RTX 5080" --max-minutes 90 --min-credit <credit - cap> \
    [--exclude-machines <id,…>]                                                   # a host that misbehaved this session
$PY -m tools.cloud.vast.cli wait --instance <id>
$PY -m tools.cloud.vast.requirements --lock-from <env python> --cuda cu128 > /tmp/requirements_cu128.txt
#   EXACT parity (§3): lock cu126 boxes (3090 / 4090 / A100) from gen3ai_torch28, Blackwell from gen3ai_torch28_cu128
for f in tools/cloud/vast/remote_bootstrap.sh tools/cloud/vast/remote_sanity.py /tmp/requirements_cu128.txt; do
  $PY -m tools.cloud.vast.cli scp-to --instance <id> "$f" /root/prov/; done
$PY -m tools.cloud.vast.cli ssh --instance <id> --detach /root/prov/run.out -- \
    "REQS=/root/prov/requirements_cu128.txt bash /root/prov/remote_bootstrap.sh setup <FULL 40-hex pushed commit> && \
     REQS=/root/prov/requirements_cu128.txt BENCH_TAG='RTX 5080 / US (cu128)' BENCH_META='--meta dph=0.344' \
     bash /root/prov/remote_bootstrap.sh bench"
$PY -m tools.cloud.vast.cli ssh --instance <id> -- 'grep "^\[gpu_bench\]" /root/prov/logs/bench.log'   # poll (≤ 55 min waits)
$PY -m tools.cloud.vast.cli scp-from --instance <id> /root/prov <local dir>
$PY -m tools.cloud.vast.cli destroy --instance <id> && $PY -m tools.cloud.vast.cli verify-zero
```

- **THE SUITE** (`src/agents/training/gpu_bench_suite.py`; its docstring is the design) is the ONE benchmark. It
  takes FIXTURES only (no `models/`, no run data, no credential), so the box needs only the public repo. Each phase
  is its own subprocess, and the result is incremental and resumable (a phase already `ok` / `oom` is skipped on a
  re-run). The phases: `host`, `update_bf16`, `update_fp32`, `headroom_b4096`, `headroom_b8192`, `collect`.
  Everything lands in ONE JSON (`gen3_gpu_bench_suite_v1`). `compare … --markdown` renders §0's table and its
  Amdahl columns. `--quick` is the CPU code path (~3 min, numbers meaningless). The LOCAL run needs the GPU lease.
- The commit must be PUSHED and passed as the **FULL** SHA. GitHub will not shallow-fetch an abbreviation, and the
  bootstrap now refuses one.
- Run every long job DETACHED on the box and poll. A dropped ssh must not kill a measurement.
- No GPU lease applies on a rented box (it is not our GPU).

## 3. cu126 vs cu128 — the comparability caveat, and how to remove it

The 5090 (Blackwell, **sm_120**) needs a CUDA 12.8 build: the +cu126 wheels' arch list stops at sm_90. So the box
runs **torch 2.8.0+cu128**, while the local 3080 Ti (sm_86) runs the shared env's **2.8.0+cu126**. The torch and
Triton versions are identical (2.8.0 / 3.4.0; the dynamo source is byte-identical, §1), and so is cuDNN (9.10.2.21).
What differs is the CUDA runtime under them: cuBLAS 12.8.4.1 vs 12.6.4.1, cuFFT, cuSPARSE, NVRTC, nvJitLink. A
cuBLAS heuristic change can move a GEMM-bound update by a few percent either way (**UNVERIFIED** for our graphs).

**To remove it:** measure the 3080 Ti baseline on cu128 too. sm_86 IS in the cu128 arch list (read on the box and
locally: `sm_70 sm_75 sm_80 sm_86 sm_90 sm_100 sm_120`), so a LOCAL cu128 environment runs on the 3080 Ti. That env now
EXISTS (2026-10-12): the conda env **`gen3ai_torch28_cu128`**, built from `environment_torch28_cu128.yml` (the twin of
`environment_torch28.yml`; `./scripts/bootstrap.sh --variant cu128`). Its pip-visible package set equals the shared
env's except the CUDA family (torch / torchvision / torchaudio `+cu128`, the 14 `nvidia-*-cu12` wheels at their cu128
pins) and the deliberately absent `asyncio` backport; the conda layer differs by the CUDA header packages (12.8.1 label)
and by patch-level drift of the `defaults` base libraries (the exact diff is in the table below). It was built beside
`gen3ai_torch28`, which was never modified. The GPU measurement is ONE script, run under a lease:

```bash
GEN3AI_GPU_LEASE_TOKEN=<token> scripts/ops/cuda_build_validate.sh run      # ~70 min, resumable; `plan` prints the cells
```

## 5. Safety rules (hard; enforced by the tool where it can)

- **The API key** lives at `~/.config/gen3ai/vastai.key` (mode 600; `api.py` refuses a group/other-readable file).
  It is read into a header and never printed, logged, returned or sent to the box.
- **Nothing private on the box.** It clones the PUBLIC repo over https. No GitHub token, no other key: ssh / scp
  use ONLY the dedicated key `~/.ssh/gen3ai_vast` (ed25519, registered on the vast account), with
  `-F /dev/null` (no ~/.ssh/config), no agent, no forwarding, and a separate known_hosts. One checkpoint may go up
  to test the path; no `models/` run dir, no credentials, no proxy config.
- **ONE instance at a time:** `create` refuses while the account lists any instance.
- **THE DEADMAN:** every `create` spawns a detached process (its own session; it survives the agent) that
  destroys the instance at `--max-minutes` or as soon as the credit falls below `--min-credit`, retrying until the
  API no longer lists it (`~/.local/state/gen3ai/vast/deadman_<id>.log`; its three exits are unit-tested in
  `deadman_test.py` — the live rental exercised only the gone-already exit).
- **The ledger** `~/.local/state/gen3ai/vast/ledger.jsonl` records every create (offer, image, credit before,
  deadline) and destroy (verified, credit after).
- **The end of every session:** `destroy`, then `verify-zero` (exit 0 only with ZERO instances) and the credit.
- **Spend:** the owner's credit is prepaid and cannot auto-top-up; the per-session cap is set as
  `--min-credit = credit − cap`. The first spend of a benchmark session needs the owner's go (memory note).

## 6. Cost model — MEASURED (2026-10-18)

A full suite session is **36-57 min wall** from `create` to a verified destroy. That is ~1-2 min to ssh, ~3 min of
setup (pip 18-44 s from the lock, the Showdown build 35-83 s, the env core ~11-21 s) and 4.5-7.2 min per update phase
(compile + parity gate + prewarm 220-345 s, then ~1 min of timed calls; 11 min on a Zen 2 EPYC). The collect phase
takes **13-21 min**, of which **T2's cold startup is 640-1,006 s**: the inference service's compile and capture,
the largest fixed cost of a rental, CPU-bound, measured nowhere in the result. The cost was **$0.26-0.80 per card**:
the listed $/h x the wall, plus storage and download (~10-20 % over the listing). The whole 9-rental ladder was
$3.54. Formula: `cost ≈ listed $/h x 1.15 x (0.7 + 0.25 per extra update phase) h`.
